# 技术实现方案 (Technical Plan)

## 1. 引擎与架构
- **引擎**：Godot 4.2 LTS (稳定版)。
- **维度**：完全 2D 开发。
- **语言**：GDScript。

## 2. 最小可行产品 (MVP) 阶段规划
严格限制开发范围，防止项目烂尾：
- **阶段 0 (核心验证)**：只做一桌普通的梭哈扑克，跑通发牌、跟注、开牌逻辑，无任何特异功能和剧情。
- **阶段 1 (技能引入)**：加入气场 (Aura) 条和最高优先级技能 A（透视眼）+ G（变个3），跑通玩家 vs AI 战斗模块。
- **阶段 2 (包装与 UI)**：加入像素风美术、UI 界面、CRT Shader 和背景音乐。技能HUD悬浮窗和Shader高亮边框。
- **阶段 3 (流程串联)**：加入对话系统，串联 3 个 Boss 关卡，形成完整的单人游戏流程。加入技能 B/C（中优先级）。
- **阶段 3.5 (双人网络)**：实现 WebSocket 匹配码连接、玩家分工、双人QTE同步，加入技能 D/E/F（低优先级）及剧情节点。

## 3. 网络实现方案：WebSocket + 匹配码

### 架构
```
玩家1 (HOST) <──WebSocket──> 信令中继服务器 <──WebSocket──> 玩家2 (CLIENT)
                              (Node.js, 无游戏逻辑)
配对完成后：
玩家1 <────────── Godot WebSocketMultiplayerPeer ──────────> 玩家2
                        (游戏数据直接P2P传输)
```

### 匹配流程
1. 玩家1点击"创建房间" → 服务器生成4位匹配码（如 `A7K3`）并返回。
2. 玩家2输入匹配码 → 服务器将双端连接信息互发。
3. 双端建立 `WebSocketMultiplayerPeer` 连接，服务器完成使命退场。
4. 游戏数据通过 Godot 高层多人API（RPC / MultiplayerSynchronizer）同步。

### 测试阶段
| 阶段 | 方法 | 成本 |
|---|---|---|
| 开发阶段 | 同一台电脑开2个Godot实例，服务器跑`localhost:8080` | 零成本 |
| 局域网测试 | 同一WiFi下两台设备连局域网IP | 零成本 |
| 线上测试 | 部署Node.js脚本到 Railway.app 或 Render.com 免费层 | 免费 |

### QTE网络规范
- QTE判定在**玩家2本地**完成，结果（成功/失败/精准等级）通过RPC上传HOST。
- 避免网络延迟影响QTE判定公平性。
- 协同输入类技能（技能G）：双端各自在本地记录按键时间戳，HOST计算时间差是否在容差范围内（建议 ≤300ms）。

## 4. 技术难点简化方案

| 原设计难点 | 简化后的替代方案 |
| :--- | :--- |
| **QTE 和 手速判定** | 单人模式**完全删除QTE**，改为回合制点击发动。双人模式QTE仅限玩家2操作，本地判定后同步结果。 |
| **扑克AI / 机器博弈** | **放弃**复杂胜率计算。改为状态机：依据当前手牌等级（对子、顺子等）赋予AI"自信值"，结合随机数决定跟注/放弃。 |
| **多玩法混杂** | **放弃**骰子和麻将。100% 聚焦梭哈扑克。 |
| **复杂 RPG 属性系统** | **放弃**自由加点。线性养成：打败Boss → 气场上限+10，剧情解锁新技能。 |
| **技能动画（透视类）** | 不翻牌面。用**悬浮半透明HUD窗口 + Shader轮廓高亮**实现，节省美术资源。 |

## 5. 第三方插件推荐
- **对话系统**：`Dialogue Manager` (Nathan Hoad) - 处理游戏内文本对话。
- **存档系统**：Godot 内置 `ConfigFile` 或 `ResourceSaver` 存储进度和金钱。

## 总结
**少即是多 (Less is More)**。通过砍掉单人QTE、多玩法和复杂RPG树，核心架构适合小团队快速实现。双人网络采用无专用服务器的WebSocket匹配码方案，最大化降低运营成本，同时保留"港片+特异功能+协作"的完整核心体验。
